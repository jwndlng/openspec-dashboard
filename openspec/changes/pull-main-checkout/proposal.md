## Why

Work happens in worktrees and is merged on the remote; a repository's main checkout only learns about it when someone runs `git pull` there. Until then the dashboard is accurate about a past state: archived changes and synced specs are read from the main checkout, the `merged` work status and every ahead/behind figure are "as of the user's last fetch", and a change that was merged and archived remotely keeps showing as open. Keeping a dozen main checkouts current by hand, in a dozen terminals, does not happen — so the overview drifts from reality exactly where it claims to give the big picture.

A second, quieter source of stale data is a main checkout that is not on its default branch. Whatever feature or release branch happens to be checked out there decides which archives and specs the dashboard sees, and nothing on the board says so.

## What Changes

- **BREAKING** (project invariants): the dashboard gains one operation that contacts a remote and updates a repository's main checkout. Today the "never writes" requirement and `CLAUDE.md` invariants 1 and 4 say the dashboard MUST NOT contact a remote and MUST NOT change the main checkout's branch, index or working tree. This change adds a single, enumerated, explicit-action exception to both, and nothing else about those guarantees changes: no network access happens on its own, on a timer, during a scan or on page load.
- **"Pull" action per repository**, in the repository board header and in the Projects overview row. On click the server runs, in the repository's main checkout, a `git fetch` of the branch's remote followed by a **fast-forward-only** update of the checked-out branch. It never creates a merge commit, never rebases, never stashes, resets, forces or switches branches, and never touches linked worktrees. Repository hooks do not run as part of it (a plain `git pull` would execute a `post-merge` hook; a click in a browser should not run repository scripts), and the result says so when such a hook exists.
- **Refused, not forced.** The fast-forward step is skipped, with the reason shown, when the main checkout is not on the repository's default branch, has no upstream, has diverged from its upstream, or has uncommitted changes the update would overwrite (git's own refusal). The fetch still happens in those cases, because it only updates remote-tracking refs — which is what makes `merged` and ahead/behind current — and cannot affect the user's files. A repository without a remote has nothing to pull and says so.
- **Credentials stay with git.** The dashboard uses whatever git already uses on the machine (SSH agent, credential helper). It never sees, stores, asks for or forwards credentials. Interactive prompts stay disabled (as for every git call today), so a remote that needs a login fails with a clear message instead of hanging; every pull has a timeout and at most one runs per repository at a time.
- **Result is reported and the board refreshes**: "already up to date", "fast-forwarded N commits", or the refusal/failure reason; a rescan of that repository follows so archives, specs, work statuses and last-updated reflect the new state without a page reload.
- **"Pull all"** on the Projects overview runs the same action for every enabled git repository, a few at a time, and lists the per-repository outcomes. It is a convenience over the per-repository action, not a different operation.
- **Notice when the main checkout is not on its default branch.** The scanner reports each repository's default branch — the branch `origin/HEAD` points to, falling back to `main`, then `master`, when the repository has no such ref — and whether the main checkout is on it. When it is not (including a detached HEAD), the Projects overview row and the repository board header show a notice, with text and not colour alone, saying that the checkout is on `<branch>` rather than `<default>` and that archived changes, specs and progress shown for this repository come from that branch and may be outdated. The notice is informational; it does not hide or alter any data. Changes that live in worktrees are unaffected by it, which the notice says.
- **Demo build**: the mock API simulates the pull (canned outcomes, including a refusal), and the sample — which already has repositories on a feature and a release branch — shows the notice. The demo still performs no network access.
- Not in this change: pulling or fetching inside linked worktrees, pushing, switching the main checkout back to its default branch, automatic or scheduled fetching, and any handling of credentials.

## Capabilities

### New Capabilities
- `repository-pull`: The explicit pull action — what it runs, the fast-forward-only rule, when the update step is refused while the fetch still runs, credentials and prompts, timeout and one-at-a-time, result reporting and the rescan, "Pull all", and what it never does.

### Modified Capabilities
- `dashboard-api`: "The dashboard never writes to tracked repositories" gains a third enumerated exception (fetch plus fast-forward-only update of the main checkout, on explicit user action) and the git subcommands it needs; the statements that the dashboard never contacts a remote and never changes the main checkout are narrowed to "except for this action". Adds the pull endpoints, behind the existing same-origin protection.
- `change-scanner`: adds that each repository's snapshot reports its default branch and whether the main checkout is on it.
- `project-overview`: adds a requirement for the not-on-default-branch notice in the overview row and the repository board header. The Pull control itself is specified in `repository-pull`. Existing overview requirements are not modified, to stay clear of `overview-tiles-and-worktree-status`, which rewrites the header requirement.
- `demo-site`: adds a requirement that the mock API simulates the pull without network access and that the sample shows the notice (added rather than modified: `demo-live-sessions` rewrites the neighbouring requirements and is not archived yet).

## Impact

- `CLAUDE.md` invariants 1 ("never contacts a remote", "main checkout … never touched") and 4 ("No network at runtime") need careful rewording: the UI still never fetches from other hosts; the server contacts a git remote only through this action. The README's statements of the same guarantees change with them.
- `src/server/`: new `pull.ts` (the only place that runs `git fetch` / `git merge --ff-only`; refusal checks with read-only git first; timeout; per-repository lock), `api.ts` (endpoints, only for enabled and successfully scanned repositories, path never taken from the request), `git.ts` / `source.ts` / `scanner.ts` (default branch and on-default flag, using the already allowed `symbolic-ref`), `src/shared/types.ts` (`RepoSnapshot.defaultBranch`, `onDefaultBranch`; pull result shapes).
- `src/ui/`: `api.ts` (operations, so the demo must implement them), `overview.tsx`, `kanban.tsx` (button, result, notice), `styles.css`, `demo/demoApi.ts`, `demo/sampleData.ts`.
- `test/`: pull tests against temporary repositories with a local bare remote (up to date, fast-forward, diverged, dirty overlapping and non-overlapping, not on default branch, no upstream, no remote, unreachable remote, timeout, concurrent request); a test that a pull changes nothing but refs, index and working tree of the main checkout and never a linked worktree; a test that scanning, polling and page load still perform no network access; default-branch detection; demo tests.
- Agent sessions are unaffected, but their work statuses become current after a pull, which is a large part of the point.
- In-flight changes touching the same requirement or files: `dedupe-discovery` and `create-change-from-dashboard` each carry a modified copy of the "never writes" requirement and must rebase on whichever lands first; `overview-tiles-and-worktree-status` (proposal and design only) adds per-checkout status to the same overview rows and header.
- Open choice carried into the design: a real pull from the dashboard (proposed) versus a "Copy pull command" button that keeps the dashboard off the network entirely. The notice and the default-branch detection are independent of that choice.
