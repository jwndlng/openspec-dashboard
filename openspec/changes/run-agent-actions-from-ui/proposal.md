## Why

The dashboard shows which changes need a proposal written or are ready to implement, but acting on that still means copying a command, switching to a terminal and starting an agent by hand — once per change, across many repositories. Starting that work from the card — and being able to keep steering it from there — is the first step from "overview" towards managing agent work centrally. The user already works with Claude Code (VS Code extension and CLI) on a Claude subscription and wants to keep using exactly that, so the dashboard should launch the locally installed `claude` CLI rather than integrate a model API of its own.

## What Changes

- **BREAKING** (project invariant): the dashboard can now *start a process that modifies a tracked repository*. The dashboard's own code still never writes to repositories (beyond what `create-change-from-dashboard` introduces); the writing is done by the user's own agent CLI, started only on an explicit click. The "read-only" promise in `CLAUDE.md` and the README is reworded accordingly.
- **Off by default, opt-in twice**: a global "Agent actions" switch in Settings, plus an opt-in per repository. Without both, the UI shows no session starters and the API refuses to open sessions.
- **Runner = the installed `claude` CLI on the user's login**: the server spawns `claude` in non-interactive print mode with streamed JSON output in the repository. It never reads, stores or forwards credentials, does not implement any login, and by default removes `ANTHROPIC_API_KEY` from the child environment so the session uses the CLI's existing subscription login instead of billing an API key (configurable). If the CLI is missing or not logged in, the action is disabled with an explanation.
- **Interactive sessions, not fire-and-forget**: every action opens a *session* bound to one change — a conversation with the agent that stays open after the first instruction finishes. The session panel shows the transcript and has an input box: the user can send further instructions ("also update the README", "skip task 3.2", "explain that failure"), answer the agent's questions, and start the next OpenSpec step in the same context. A session is `running` while the agent works and `waiting` when it is the user's turn; it ends only when the user closes it, cancels it, or it fails. Follow-ups continue the same underlying CLI session, so context is kept and the conversation can be resumed after a dashboard restart.
- **Two session starters in v1**, offered only where they make sense:
  - **Draft artifacts** — for changes whose artifacts are incomplete: runs the project's OpenSpec continue/fast-forward command for that change (using the change's `prompt.md` when present).
  - **Implement** — for changes in `Ready` or `Implementing`: runs the project's OpenSpec apply command for that change.
  The opening instruction is a fixed template built from the validated change name. Follow-up messages are free text, but they are delivered to the agent as conversation messages over the session's input channel — never interpolated into a command line or a shell.
- **Bounded permissions, never bypassed**: sessions use a non-interactive permission mode with an explicit tool allow-list (per repository, with a conservative default: file read/edit and the `openspec` command) on top of whatever the repository's own `.claude/settings.json` allows. The dashboard never passes a "skip all permissions" flag; a tool call outside the allow-list is denied and shown in the transcript, so the user can respond in the session (rephrase, or widen the repository's allow-list in Settings) instead of the agent hanging on an invisible prompt.
- **Where a session works**: in place in the repository by default. A per-repository option opens it in a fresh git worktree on a branch named after the change (via the CLI's worktree support), offered only when the change's directory is committed — uncommitted artifacts would be missing in a worktree.
- **Session lifecycle and visibility**: states `queued → running ⇄ waiting → closed | failed | cancelled | interrupted`; one open session per change and a global limit on concurrently *running* sessions (default 2; waiting sessions do not count). Cards show a session badge that distinguishes "agent working" from "waiting for you"; the session panel shows the live transcript (user messages, assistant text, tool calls and results, per-turn cost/usage when reported), the input box, Stop (interrupt the current turn) and Close, and a **"Copy resume command"** with the session id so the same conversation can be continued in a terminal or the VS Code terminal at any point. Usage-limit and authentication errors are surfaced as such.
- **Session records live outside repositories**: `~/.openspec-dashboard/sessions/<id>/` holds metadata (repository, change, CLI session id, state) and the transcript event log, with retention (last N closed sessions). On dashboard shutdown running children are stopped and the session is marked `interrupted`; because the CLI session id is stored, an interrupted or waiting session can be reopened and continued.
- **Hardened API**: session endpoints are mutating and rely on the cross-site request protection introduced by `create-change-from-dashboard` (this change lands after it); processes are spawned without a shell from an argument array; repository must be enabled, scanned and opted in; change names are validated.
- Non-goals for v1: agents picking up work on their own or scheduling, other agent CLIs (the runner is written behind a small interface, but only `claude` ships), approving individual tool-permission requests from the UI (denied calls are reported; the allow-list is changed in Settings), sessions not bound to a change, archiving from the UI, committing/pushing/opening pull requests, remote or multi-machine execution.

## Capabilities

### New Capabilities
- `agent-sessions`: opening and conducting interactive agent sessions from the dashboard — enablement and per-repository opt-in, the session starters and when they are offered, how the CLI is invoked (login, environment, permissions), the dedicated worktree each session works in and its clean-up, sending follow-up messages, session states and limits, stopping a turn and closing or cancelling a session, the transcript and resume hand-off, reopening after restart, session storage and retention, and failure modes (CLI missing, not logged in, usage limit, permission denied).

### Modified Capabilities
- `dashboard-api`: adds session endpoints (open, list, read/stream transcript, send message, stop turn, close/cancel) with their validation and refusal cases; rewords "the dashboard never writes to tracked repositories" to the new boundary (the dashboard's code does not write; it may start the user's agent on request).
- `kanban-board`: cards gain the session starters appropriate to their stage, a session badge (working / waiting for you / failed), and access to the session panel; existing copy actions remain.
- `repo-discovery`: configuration gains the global agent-actions switch and per-repository session settings (opt-in, allowed tools), editable in Settings.

## Impact

- Server: new `src/server/sessions/` (runner interface, `claude` runner, process supervision, message input, transcript storage), `src/server/api.ts` (endpoints, server-sent transcript stream), `src/server/config.ts` + `src/shared/types.ts` (settings, `Session` types), shutdown handling in `src/server/index.ts`.
- UI: session starters and badge in `src/ui/kanban.tsx`, a new session panel (transcript + input), Settings additions, `src/ui/api.ts`, styles. If `add-change-detail-view` lands first, the session panel is also reachable from the change detail view.
- Docs/invariants: `CLAUDE.md` invariant 1, README headline statement, `CONTRIBUTING.md` note on testing without a real agent.
- Tests: a fake runner executable for lifecycle, multi-turn follow-ups, stop/close/cancel, concurrency, permission-denied, crash and reopen-after-restart cases; endpoint refusal cases; no test invokes the real CLI or network.
- Dependencies: none added; requires the user's own `claude` CLI at runtime (optional feature). First task is a short spike verifying the assumed CLI behaviour (subscription login in print mode, streamed JSON output shape, multi-turn input — a long-lived process fed over streamed JSON input versus one invocation per message resuming the session id —, resume from a terminal, worktree flag, permission-mode semantics and how denied tool calls are reported) before the design is fixed.
- Ordering: depends on `create-change-from-dashboard` (request protection, `prompt.md`); touches `src/ui/kanban.tsx` alongside `add-change-detail-view` and `collapsible-repo-groups`.
- Risk: an agent started from a browser click edits real repositories — mitigated by double opt-in, allow-lists, no permission bypass, one run per change, visible logs and cancel.
